### 2. Data quality issue resolution for 1Z shipments

**Context:** When the 78 shipments were stuck as `icris_missing` / `invalid_icris` (source ICRIS was `'-'` — a CRM placeholder dash), each had open `crm_invalid_icris` or `crm_blank_icris` data quality issues. The `backfill_1z_icris_extraction` function calls `link_icris()` which already contains the resolution logic (`crm_sync.py:78`): on successful match it sets those open issues to `status='resolved'`, `resolved_by='crm_sync'`.

So after the backfill ran, all 78 shipments that moved to `match_status='matched'` also had their data quality issues auto-resolved — no manual cleanup needed.

**Ongoing:** future syncs also benefit — any new 1Z shipment that previously would have logged `crm_invalid_icris` (because `Icrisno` was `'-'` or blank) now gets the ICRIS extracted from the tracking number and matches cleanly, so those data quality issues never get created in the first place.

### 7. Active Pipeline sync — converged robust path

**Context:** The Active Pipeline sync was the only CRM sync path with no durability infrastructure — no `CrmSyncRun` record, no validation, two divergent fragile entry points (HTTP route + scheduler), and a frontend that couldn't tell a failed fetch from an empty pipeline.

| File | Change |
|---|---|
| `backend/app/crm_sync.py` | Added `run_active_pipeline_sync(db, html, source_url, *, dry_run=False, worker_id=None)` — creates a `CrmSyncRun`, validates with `looks_like_login()` (raises `SessionExpired` on session-expiry pages instead of silently parsing zero rows), catches `CrmParseError`, and adds a row-count collapse guard (`PIPELINE_SNAPSHOT_MIN_RATIO = 0.4` — refuses a snapshot that's <40% of the prior row count, treating it as a partial-render symptom rather than a genuine pipeline shrink). Commits failure/warning runs before raising so they survive the caller's rollback. |
| `backend/app/main.py` | `POST /crm-sync/active-pipeline` route now calls `run_active_pipeline_sync` and returns `crm_run_payload(db, run)`, matching every other sync endpoint's response shape |
| `backend/app/crm_worker.py` | `check_pipeline_auto_schedule` now calls the same `run_active_pipeline_sync`; its `emit()` reflects the real run status (`completed` / `completed_with_errors` / `failed`) instead of a flat `synced` |
| `backend/tests/test_pipeline_sync.py` | 5 new tests: run creates a completed `CrmSyncRun`, login-page detection marks the run failed and retains existing rows, suspicious row collapse is refused, a normal-sized snapshot goes through, bad HTML structure marks the run failed |
| `frontend/src/pages/Pipeline.tsx` | Reworked: distinct error state (rose banner) instead of looking like an empty pipeline; staleness pill when `as_of` is >24h old; revenue-at-risk total folded into the "needs follow-up" badge; table switched to `table-fixed` + `colgroup` so it fits without horizontal scroll; Remarks moved from an always-visible column to a click-to-expand row (icon-only column header) |
| `frontend/src/pages/CrmSync.tsx` | Added a pipeline sync trigger with result/error banners (later merged into the single "Trigger Sync" button — see item 3 above) |
| `frontend/src/api.ts` | Added `CrmSyncRunPayload` type; `syncPipeline()` now returns it instead of `any` |

Both entry points now share one validated, run-tracked path. Pipeline syncs appear in the CRM Sync runs history like every other sync type.
