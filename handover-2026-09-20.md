## 1. Light/Dark Theme Toggle — DONE, committed, pushed

**Status:** Complete. Commit `bd15e5c` on `main`, pushed to `origin/main`.

### Problem
The app was hardcoded to dark: `<html class="dark">` was a static literal, and `frontend/src/index.css` defined the whole color system with dark values only. No toggle infrastructure existed at all.

Dark styling had accumulated in three inconsistent patterns, all assuming dark-only:
- **Raw `zinc-*` utilities** (369 occurrences across 15 files, e.g. `bg-zinc-950 text-zinc-50` in `app-shell.tsx`) — hardcoded, no light counterpart.
- **Semantic tokens** (`bg-background`, `text-foreground`) — resolved to dark hex in `@theme`.
- **Light classes force-darkened** (`bg-white`, `text-slate-900`) via an `!important` override block in `index.css` — this markup was *authored as light* and force-flipped.

### Fix (CSS-first, no per-component edits needed for the 369 raw-zinc lines)
1. **Inverted the token layer** in `frontend/src/index.css`: `@theme` now holds light values by default; dark values moved under `.dark { --color-*: … }`. Tailwind v4 utilities compile to `var(--color-*)`, so this cascades everywhere automatically.
2. **Scoped the `!important` force-dark block to `.dark`** — light-authored markup (`bg-white`, `text-slate-900`, `shadow-sm`) now reverts to its natural light styling when `.dark` isn't present.
3. **Added a light-mode inversion layer for raw `zinc-*` classes** — mirrors Tailwind's zinc scale (50↔950, 100↔900, …) so the 369 raw-zinc occurrences across 15 files get correct light-mode colors with **zero edits to those files**.

### Files changed
- `frontend/src/theme.tsx` (new) — `ThemeProvider` + `useTheme()`, persists to `localStorage`, follows `auth.tsx`'s context pattern.
- `frontend/index.html` — removed static `class="dark"`; added a blocking inline `<script>` in `<head>` that reads `localStorage.theme` (falling back to `prefers-color-scheme`) before paint, so there's no flash of the wrong theme.
- `frontend/src/main.tsx` — wraps app in `<ThemeProvider>`.
- `frontend/src/components/app-shell.tsx` — sun/moon toggle button in the header (`lucide-react` `Sun`/`Moon`), wired to `useTheme()`.
- `frontend/src/index.css` — the CSS work described above.

### Bug caught during verification (worth knowing for future CSS work here)
First pass used `:not(.dark) .foo` as the light-mode override selector. That's wrong — `:not(.dark)` as a *descendant combinator* matches any ancestor that isn't itself the `.dark` element (e.g. `<body>` always qualifies, since `.dark` lives on `<html>`), so the rule never actually turned off. **Fix: scope to `html:not(.dark) .foo`** — 40 selectors in `index.css` use this now. If you add more light/dark override rules by hand, use `html:not(.dark)`, not bare `:not(.dark)`.

### Verification done
- `npx tsc -b --noEmit` and `npm run lint` — clean (only pre-existing warnings, nothing new).
- Browser-driven checks (via computed-style scans, not screenshots — the preview pane didn't support screenshot in this session): zero dark-color leaks in light mode, zero light-color leaks in dark mode, dark mode confirmed pixel-identical to pre-change baseline (regression-safe), toggle persists across reload, checked on Executive Overview (charts/KPIs), Customer Directory (table), and app-shell/header (heaviest raw-zinc file — 52 occurrences).
- Did **not** pixel-walk every one of the ~15 flagged pages individually — the fix is CSS-only and mechanically covers all of them since they reuse the same class vocabulary (zinc-800/900/950, text-zinc-*, border-zinc-*) already remapped in `index.css`. If a specific page still looks wrong in one theme, it's almost certainly a missing selector in the `html:not(.dark)` block or `.dark` block in `index.css` — check there first.

### Problem being solved
User said the page (at `/app/profitability`, "probability" was a typo) "looks not informative and too overwhelming." Diagnosis from reading the live page (`frontend/src/pages/Profitability.tsx`):

1. Six stacked full-width sections, all equal visual weight — no hierarchy, no "so what" up top. The actual Profit/Loss number is the 3rd of 4 identical KPI cards.
2. "Profit by Route" chart is often near-empty — live data showed "Top 1 routes" (a single bar), because most MAWBs share one route.
3. "Profit by Customer" table is **always empty** in practice — "No per-shipment UPS data for this range yet" — depends on a separate UPS-detail sync that's usually missing.
4. "Margin Leaders" (Best/Top $/Lowest cards) duplicates what sorting the MAWB Detail table by margin already shows.
5. Two dense tables with identical columns (Billed/UPS Cost/Profit/Margin) read as redundant.
6. ECharts trend/route charts hardcode light-only colors (`#fff`, `#0f172a`, `#e2e8f0` for tooltip/axis) — will render wrong in dark mode now that the toggle exists.

- **Cutting:** Cut & auto-hide — remove Margin Leaders entirely (redundant); auto-hide Profit-by-Route when ≤1 route; auto-hide/remove Profit-by-Customer since it's always empty.
- **Chart theming:** Yes, fix dark mode for the charts as part of this redesign.
